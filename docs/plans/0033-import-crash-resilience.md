# 0033 大批量导入稳定性与内存保护

> 本计划已由 `docs/plans/0036-thumbnail-only-decode.md` 收紧为当前契约。文中
> “原图解码”只表示历史问题背景；当前导入和分析不得建立完整源图像素缓冲区。

## 问题

大批量导入时，扫描器最多同时处理 4 个图像任务。模型自动恢复后，ONNX
会话与图像处理内存会叠加；旧图像解码器的默认单图分配上限仍可能达到
512 MiB。高像素图片、异常图片或多个大文件同时处理时，会造成明显卡顿、
导入任务中断，极端情况下进程退出。当前实现通过 bounded thumbnail decoder
避免把完整源图像素交给导入/分析链路。

## 方案

- 将导入图像 worker 限制为 1–2 个，降低 bounded thumbnail extraction 峰值；缩略图缓存复用路径仍可并行。
- 所有导入和缓存重算只使用应用私有缩略图或有界缩略图派生输入。Windows
  首次导入优先使用内嵌预览，否则使用 WIC bounded decoder；不支持 bounded
  提取的格式明确失败。screen 预览也使用有界输出，`original` 只保留为用户
  主动查看的独立例外。
- 保留 640×640 缩略图和已有的缩略图优先分析逻辑；超出安全限制的图片只标记当前文件失败，不读取无限大的像素缓冲区。
- worker 使用 panic 隔离和带原文件上下文的失败结果，单张图片异常不会让整次扫描线程崩溃。
- “重新扫描”沿用图库的嵌套 SourceRoot 列表，父图库发起重扫时同步覆盖已登记的子图库。

## 验收

- 100、300 张普通 JPEG/PNG/WebP 夹具可完成冷导入，应用不退出。
- 高像素或损坏图片出现可解释的单文件失败，剩余图片继续处理。
- 导入期间 CPU/内存峰值较原 4 worker 版本降低；扫描进度和 SQLite 结果保持一致。
- 已有缩略图的重扫继续走缓存路径，不重新解码原图像素。
- 重新扫描父图库后，已登记子图库中的新增、修改和缺失文件也会被处理。

## 验证

- Rust 单元测试、导入基准、桌面特性编译、前端测试和资源校验。
- 不读取或修改用户个人照片目录；性能验证只使用 `benchmark-output/` 隔离夹具。
