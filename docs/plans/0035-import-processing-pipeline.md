# 0035 导入处理流水线与批量落库

## 问题

有界发现窗口解决了重资源积压，但处理端仍然逐张执行 SQLite 事务、每 1–2 张创建一次 worker 线程；同时颜色特征计算会对同一缩略图像素重复转换到 OKLab。大量图片时，处理吞吐被线程创建、CPU 计算和事务提交共同限制。

## 方案

- 在缩略图分析中缓存采样网格的 OKLab 值，复用到当前像素和局部对比度邻居计算。
- 发现完成后只处理已收集的路径列表，不预读图片字节；按 16 张形成处理批次，每批最多使用 2 个 worker，单个 worker 在批次内连续处理多张图片，避免逐图创建线程。
- 处理结果达到固定批量后一次事务写入 assets、thumbnails、tone_features 和 color_features。
- 保留单图处理失败记录；批量数据库事务只承担已经完成的结果写入，数据库错误仍会中止当前扫描并记录任务错误。
- 继续使用缩略图进行基础特征分析；源图只承担必要的 EXIF、尺寸、指纹和首次有界缩略图提取，禁止完整源像素 decode。

## 验收

- 特征计算的重复 OKLab 转换显著减少，颜色结果和已有测试保持稳定。
- 1000 张隔离图片的处理吞吐提高，数据库写入次数从逐图事务降低为批量事务。
- 单图损坏、取消、缓存重算和父子图库扫描行为不回归。

## 验证

- Rust 单元测试、clippy、桌面编译和前端回归。
- 使用隔离的 1,000 张 `320×240` 生成 JPEG 基准比较处理阶段耗时，不访问用户个人照片目录：当前 release 冷导入 `16.3s`，`feature_analysis_us` `20.8s`，`database_write_us` `1.00s`；缓存重算 `14.9s`（特征分析 `20.0s`、数据库 `0.79s`）、热重扫 `3.7s`，三次均 1,000/1,000 完成且失败为 0。
