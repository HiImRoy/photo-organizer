# ADR 0005：本地搜索与照片工作流扩展架构

- 状态：Proposed
- 日期：2026-08-09
- 关联计划：[Plan 0018](../plans/0018-lap-inspired-library-expansion.md)
- 参考项目：[julyx10/lap](https://github.com/julyx10/lap)（审计提交 `590ed3d04d17ece2feb763cc48d86b4ceb20176a`）

## 背景

PhotoOrganizer 已经具备 Tauri 2、React/TypeScript、Rust、SQLite、JPEG/PNG/WebP 只读扫描、缩略图、EXIF、连续影调/色彩特征、TinyCLIP INT8 CPU 推理、512 维图像向量、人工分类覆盖、星级/色标、单图预览和整理 dry-run。下一阶段希望增量加入收藏与集合、更成熟的图库浏览、比较、精确重复检测、文本/相似图像搜索、相似图像聚类、面部聚类以及非破坏性图像编辑。

这些能力会同时影响数据模型、后台任务、模型分发、缓存、IPC、前端工作区和文件安全，属于显著架构扩展，必须先形成决策记录。

Lap 提供了可验证的产品和实现参考，但存在三个不能直接照搬的条件：

1. Lap 使用 Vue、Pinia、Tailwind 和 daisyUI；当前项目使用 React 和自有 CSS 令牌。
2. Lap 使用 GPL-3.0-or-later；当前项目声明 MIT OR Apache-2.0。
3. Lap 允许移动、覆盖和移入废纸篓；当前项目禁止修改或删除原图，COPY 和 dry-run 是安全边界。

## 决策

### 1. 保持单进程 Rust 核心，不引入 Python sidecar

继续使用：

- Tauri 2 desktop shell；
- React + TypeScript 前端；
- Rust 领域服务、任务执行和文件安全边界；
- SQLite 作为唯一权威目录与用户数据存储；
- 现有动态加载的 ONNX Runtime CPU 后端；
- AppData 下的可重建缩略图、预览和向量索引缓存。

首轮实现不增加 Python/OpenCV sidecar，不引入远程后端，不要求账号或云服务。如果 YuNet/SFace 无法通过现有 ONNX Runtime 可靠执行，停止在人脸模型 PoC，不以“先跑起来”为理由静默加入 Python 或 OpenCV runtime；届时必须另写 ADR。

### 2. Lap 仅作为行为和算法参考，不复制 GPL 源码

允许：

- 对照 Lap 的信息架构、工作流、数据关系和公开算法思路；
- 在设计文档和代码注释中链接到固定提交；
- 独立实现通用算法，例如 BLAKE3 分组、余弦相似度、HNSW 邻居搜索和 Chinese Whispers 聚类。

不允许：

- 复制 Lap 的 Rust、Vue、CSS、SVG 或其他受 GPL 约束的实现文件；
- 将 `reference/lap` 纳入构建、打包或发布；
- 在没有单独许可证评审的情况下复用 Lap 分发的模型权重或二进制资源。

如未来确实需要并入 Lap 代码，必须先决定是否接受 GPL 传播义务或取得其他授权；本 ADR 不授权该行为。

### 3. 目录数据、人工组织、派生内容继续分层

保持以下边界：

- `assets` 描述扫描到的物理原图；
- `libraries` 和现有 assignment 描述来源与当前虚拟图库归属；
- 收藏、集合、保存视图、重复审阅状态、人物簇和编辑配方只存在于本地数据库；
- 图像编辑输出是新的 `derived asset` 或外部导出副本，不能原地覆盖 `assets.absolute_path`；
- 向量索引和预览是缓存，不是权威数据，可从 SQLite 与原图重建。

### 4. 先复用现有 TinyCLIP，再按证据升级向量索引

当前 `semantic_embeddings` 已保存 512 维图像向量和模型/版本/源指纹，因此图像相似搜索不重新推理已分析图片。将 `TinyClipClassifier` 抽象为可同时提供以下能力的本地视觉语言模型：

- `classify(images)`：保留现有标签分类；
- `encode_text(query)`：生成文本向量；
- `encode_images(images)`：供缺失/失效向量补算；
- `metadata()`：返回模型、版本、分析版本、维度、许可证和校验和。

搜索实现分两层：

1. 精确余弦检索作为正确性基线、测试 oracle 和小图库 fallback；
2. 当 25,000 个有效向量以上，或基准显示 P95 搜索时间超过 200 ms 时，允许加入 Apache-2.0 的 [`hnsw_rs`](https://docs.rs/hnsw_rs/latest/hnsw_rs/) 作为 HNSW 实现。

HNSW 只保存于 AppData 缓存，索引键必须包含图库 scope、模型名、模型版本、分析版本、维度和数据版本。任何不匹配都触发重建，不能返回跨模型相似度。

首轮文本搜索使用当前 TinyCLIP 的 tokenizer 和英文语义空间。中文输入先通过项目维护的有限本地词典和短语映射形成英文 prompt，同时在 UI 明示当前语言能力。多语言文本模型属于可选后续模型包，必须独立记录体积、许可、校验和、质量基准和安装策略；不照搬 Lap 的运行时下载流程。

### 5. 相似图像分组使用“近邻候选 + 精确复核 + 紧致分组”

相似分组不能简单按传递闭包合并，否则 `A≈B`、`B≈C`、`A≉C` 会形成质量差的大组。采用：

1. HNSW 为每个向量生成 Top-K 候选；
2. 对候选重新计算精确余弦；
3. 使用互为近邻或 complete-link 阈值构建紧致组；
4. 选取组内平均相似度最高的图片作为代表；
5. 将 scope、模型版本、阈值和源数据版本写入扫描会话。

阈值不硬编码为 Lap 的 `0.93`。通过项目自己的正负样本评估集确定默认值，并允许用户在“严格 / 平衡 / 宽松”预设间切换。

### 6. 人脸功能是显式选择加入的“面部聚类”，不是身份识别

首选模型候选：

- 检测：OpenCV Zoo YuNet；其模型目录声明 MIT；
- 对齐与特征：OpenCV Zoo SFace；其模型目录提供 Apache-2.0 许可证。

不使用 Lap 当前引用的 InsightFace `det_500m.onnx` 和 `w600k_mbf.onnx` 权重。InsightFace 代码为 MIT，但官方说明其公开预训练模型/训练数据通常仅限非商业研究用途；这与当前项目的可分发许可目标不匹配。

实现要求：

- 模型在本地运行，资源随应用或经离线安装包提供；
- 每个模型包含来源、许可证文本、SHA-256、输入输出契约和版本 manifest；
- 默认不开启面部索引，首次开启前解释本地生物特征数据的用途；
- 提供“删除全部面部数据和索引”命令；
- 仅生成未命名人物簇，用户可本地重命名；不将簇名称解释为真实身份；
- 面部向量不离开本机，不写入原图元数据，不参与普通导出；
- 同一张照片内的不同人脸不得直接互相连边；
- 聚类使用 HNSW k-NN 图、精确余弦和可复现的 Chinese Whispers，避免 Lap 当前 O(N²) 全量配对在大图库上的扩展问题。

若 YuNet/SFace 的模型许可、输出契约或质量验收任一不通过，面部里程碑保持 blocked，不替换为许可不明模型。

### 7. 图库虚拟化选择无样式 React 适配器

采用 MIT 的 [`@tanstack/react-virtual`](https://tanstack.com/virtual/latest/docs/framework/react/react-virtual) 作为唯一新增前端运行时依赖候选，用于大图库行/网格窗口化。原因：

- headless，不强制视觉体系；
- 支持测量、overscan、稳定 key 和滚动定位；
- 可继续使用现有 `AssetCard` 与 CSS 令牌；
- 避免复制 Lap 的自定义 Vue 虚拟滚动实现。

依赖仅在浏览器性能基准和 PoC 通过后加入并锁定版本。React 19 下将从 `useFlushSync: false` 开始验证。数据层仍使用分块查询和窗口缓存，虚拟 DOM 不能退化为一次加载全部图片。

不引入 Tailwind、daisyUI、Pinia 或整套组件库。

### 8. 比较工具复用预览控制器，图像编辑采用配方 + 新副本

比较工具：

- 从现有 `usePreviewController` 抽取可复用 pane controller；
- 先交付双栏，再扩展到四栏；
- 每个 pane 独立导航，按需同步缩放和平移；
- 同时最多持有四张 screen preview，原图按显式请求加载；
- 收藏、星级、色标和选片状态通过现有资产更新 API 同步。

图像编辑：

- 编辑配方（旋转、翻转、裁剪、缩放、亮度、对比度、饱和度、色相）存于 SQLite；
- 预览由低分辨率后端渲染，导出由相同 Rust pipeline 在全分辨率执行；
- 浏览和保存配方不写原图；
- 默认“另存为副本”，目标存在即失败；
- 执行前生成不可变预览，复核源指纹与目标边界，先写操作日志；
- 仅允许回滚应用生成且指纹仍匹配的副本，不删除原图。

编辑导出依赖安全 COPY/操作执行基础完成。该依赖未完成前，只交付配方和预览，不提供写盘按钮。

### 9. 重复清理不采用删除语义

精确重复检测直接复用当前扫描生成的完整 BLAKE3 `assets.fingerprint`，先按 `file_size` 缩小候选，再按 fingerprint 分组。首轮不重复读取所有原图，也不创建第二套 hash authority。

“清理”在当前安全政策下指：

- 审阅重复组并选择保留项；
- 将其余项标记为在后续整理/导出中排除；
- 生成“唯一副本集”导出计划；
- 导出审阅报告。

不提供移入废纸篓、永久删除、移动、重命名或覆盖。未来若要删除原图，必须由用户明确改变产品安全原则，并单独撰写 ADR、恢复方案和端到端安全测试。

## 被否决或延期的方案

### 直接 fork 或移植 Lap

否决。技术栈、许可和原图操作语义均不匹配，也会破坏当前增量路线。

### 使用 SQLite 向量扩展作为首选

延期。当前应用使用 bundled SQLite；引入原生向量扩展会增加跨平台打包、ABI 和安全维护成本。首轮由 Rust 搜索服务和可重建 HNSW 缓存承担。

### 一开始就替换 TinyCLIP

否决。现有向量已经覆盖分类和相似搜索，先复用能避免全库重算。只有多语言质量评估明确不达标且新模型许可/体积可接受时才新增模型族。

### 使用浏览器 CSS filter 作为最终编辑结果

否决。CSS 预览与后端编码结果难以保证一致；最终预览和导出必须共用 Rust 参数语义。

### 直接使用 Lap 的人脸模型

否决。除 GPL 来源边界外，相关 InsightFace 权重的公开许可不能满足当前可分发目标。

### 在重复清理中调用系统废纸篓

否决。与“永不删除原图”和当前 MVP 安全约束冲突。

## 影响

### 正面影响

- 最大限度复用现有扫描、向量、任务、预览和 SQLite 基础；
- 保持单机、离线、无账号架构；
- UI 可借鉴 Lap 的成熟工作流，同时保留 PhotoOrganizer 的视觉身份；
- 文件写操作仍有统一的 preview、fingerprint、no-overwrite 和日志边界；
- 模型和索引具备明确版本、许可和失效策略。

### 成本与风险

- `App.tsx` 当前承担过多状态，新增工作区前必须先拆分 shell、query、selection 和 task state；
- 虚拟网格和分块查询会改变现有分页测试；
- TinyCLIP 对中文自由文本能力有限；
- HNSW 索引重建会占用 CPU 和内存，需要取消、进度和资源上限；
- 面部聚类涉及敏感本地数据和模型质量，必须提供显式 opt-in 与清除能力；
- 编辑导出依赖尚未完成的安全操作执行基础。

## 验证门槛

本 ADR 只有在以下门槛满足后才能从 Proposed 改为 Accepted：

1. `@tanstack/react-virtual` PoC 在 10,000 个模拟条目和真实缩略图夹具上无明显空白、跳动和选择丢失；
2. 精确搜索基准建立，HNSW 引入条件可由数据触发；
3. 任意文本编码与当前图像 embedding 维度/归一化契约验证通过；
4. YuNet + SFace 的模型来源、许可证、校验和和 Windows CPU PoC 归档；
5. 所有新增模型和依赖通过许可证清单；
6. 编辑导出共享安全 executor 的设计通过审查；
7. 所有文件系统测试只使用 `test-data/` 和临时输出目录，源夹具前后 hash 相同。
